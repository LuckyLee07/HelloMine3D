# HelloMine3D Stage 9 / Beta 迭代路线

本文是 Release Candidate 之后继续把 HelloMine3D 推进成“更像完整单机游戏”的权威预排
路线。它固定开发顺序、范围边界、版本策略和回归合同，方便后续逐批实施和复盘；当前状态、
历史任务数量仍以 `docs/todolist.md` 为准，已经完成的自动化证据仍以
`docs/runtime-validation.md` 为准。

最后更新：2026-08-21。

## 状态和统计边界

- `Planned` 表示已经排定方向，但尚未成为当前 `Todo` 或 `Doing`。
- `N7-N12` 和 `BETA-RC` 不计入拆分前的 77 项正式总账，也不改变当前
  `73 Done / 4 Verify / 0 Doing / 0 Todo`。
- 只有开始某个批次时，才在 `docs/todolist.md` 建立该批的正式任务和合同；不得一次性把
  后续所有细项转成活跃待办。
- 每批开始前先固定合同和版本边界，完成后再记录真实测试数、性能数据和提交，而不是把本文
  的预期值当作已经取得的证据。

依赖顺序原则上是
`RC0 -> N7A -> N7B -> N8A -> N8B -> N9A -> N9B -> N10 -> N11A -> N11B -> N12A -> N12B -> N12C -> BETA-RC`。
其中 N11B 和 N12C 是可后置伸缩项：首个 Beta 可以在 N11A、N12A、N12B 完整且验收通过后
决定是否纳入，但不能用删除基础难度、本地化或正式音效来换取排期。
可以在不改变共享存档/资源格式时提前准备 N12 的许可证和文案清单，但不能并行合入多个会
同时改写世界身份、目标链或玩家状态的批次。

## RC0：基线收口

目标：先为现有 RC 建立可恢复、可人工确认的起点，避免带着模糊基线进入新内容开发。

范围：

1. 重新生成覆盖“线上基线到当前 HEAD”全部未推送提交的 Git bundle，并执行
   `git bundle verify`；bundle 放在仓库外或明确忽略的位置，不进入发行包。
2. 核对 `docs/todolist.md`、路线图和运行证据的状态一致性。
3. 在目标 Windows Release 构建上执行 `docs/manual-input-acceptance-v1.md` 的 R3 十二项
   真人输入记录；完成后同步关闭 D2、D4 和 D6。
4. R3 通过后可创建本地 RC 标签；是否推送仍需用户另行明确授权。

执行边界：

- 自动化 EXE 一律隐藏或后台运行；R3 因需要真人输入和观察，可以在事先安排的窗口前台运行。
- 本批不增加玩法、不改存档版本、不重批性能预算。
- Git 提交和标签只保存在本地，不 push。

退出条件：bundle 校验通过，文档状态一致，R3 记录通过，D2/D4/D6/R3 全部关闭，且工作区
不把 `tmp/` 或本地产物混入提交。

## N7A/N7B：结局状态、文本键与首个胜利闭环

玩家问题：当前目标链在“修复路标”后结束，已有探索终点但缺少高潮、结果反馈和可继续辨认的
世界状态。

内部交付顺序：

1. `N7A` 先新增独立的 `WorldOutcomeState`/`VictoryFlow`。至少区分未开始、已激活、遭遇中、
   已胜利和奖励已领取；它是世界列表标记、恢复和一次性奖励的唯一事实来源。
2. `N7A` 同时建立语义化文本 key、`en-US`/`zh-CN` 资源、缺失 key 回退和开发期诊断。
   目标定义不再继续扩张硬编码玩家文案，也不采用 MiniGame 的数字字符串 ID。
3. `N7B` 为 Waystone 增加可理解的激活配方或仪式，材料复用现有铁级、食物、敌人掉落和
   生态资源。
4. `N7B` 先使用现有 Stalker/Brute 或仅调整数据参数的精英敌人组成固定波次。数量、生成距离、
   失败恢复和离场行为必须有上限；专属 Guardian/Boss 行为延后到 N8 证明需要后再立项。
5. 完成后展示胜利覆盖层、目标结果和世界列表完成标记；应用状态继续保持 `Playing`，玩家可
   关闭覆盖层并继续沙盒，不新增独立 Victory 应用阶段。
6. 奖励、目标事件和路标状态必须幂等；重复加载、重复交互或崩溃恢复不能重复发奖。
7. 增加约 3-5 个终局目标，把现有 23 项目标串到准备、激活、防守和完成。目标负责引导和
   描述，不得再用“当前没有可见目标”推导世界已经胜利。

批次开始时建立 `waystone-victory-contract-v1.md`，先固定结局状态权威、事件状态机、失败
语义、奖励 epoch/领取标志、文本 key、保存格式和 UI 快照边界。预计世界保存升级到 v9；
这是预排编号，只有合同确认确实新增持久字段后才锁定，不能为了编号整齐空升版本。

最低回归：

- 新世界正常路径无需 debug 注入即可完成胜利。
- 激活前、中、后保存和重开；旧 v1-v8 fixture 迁移；非法阶段值拒绝或安全归一；世界列表只
  从持久结局状态生成完成标记。
- 重复事件、满背包奖励、死亡、暂停、卸载路标区块和恢复备份均不复制状态或物品。
- 中英文终局 key 集合一致；缺 key、未知语言和非法文本资源按合同安全回退。
- 守卫数量、掉落、目标进度、事件队列和驻留区块均满足既有上限；运行相关 Q1 场景和短时
  nominal/stress soak。

明确不做：独立 Victory 应用阶段、多结局、剧情对话树、过场动画系统、通用任务管理器、
专用 Boss 框架、无限事件或在线成就。

退出条件：干净新世界能沿正常玩家路径获得一次清晰胜利；重启后胜利、奖励和世界列表标记
一致；胜利后继续游玩不会重复触发终局事件；定向回归、迁移和性能护栏全部通过。

## N8A/N8B：战斗可读性与远程遭遇

玩家问题：当前近战和敌人差异已经可用，但敌我意图、空间压力和应对选择仍不足以支撑终局
守卫战和后续营地探索。

内部交付顺序：

1. `N8A` 先交付攻击前摇/预警、方向性受击反馈、短硬直或击退；逻辑判定和视觉表现保持
   分离，让 N7B 守卫战无需等待投射物也具备可读性。
2. 将敌人定义扩展为小型、版本化的战斗档案，覆盖近战/远程模式、攻击距离、前摇、恢复、
   冷却以及必要的投射物参数；状态机限制为 Idle/Chase/Windup/Recover 等显式状态。
3. `N8B` 再增加一种远程敌人和有界投射物：固定 tick、寿命、最大距离、速度、伤害、碰撞、
   遮挡和全局/活动区上限均由定义控制。
4. 投射物只保存发射者 ActorId 等稳定身份，属于瞬态状态，不写入世界保存；保存重开、区块
   卸载、发射者死亡、超时或越界都必须清理。
5. 增加最低限度防御，例如盾牌或格挡；先验证时机与资源取舍，不建设复杂护甲树。
6. 增加调试快照：敌人当前状态、目标 ID、最近转换原因、活动投射物数量/上限以及本 tick
   使用的射线或寻路预算。目标失效时必须安全回到可恢复状态。

批次开始时建立 `combat-encounter-contract-v1.md`，固定敌人战斗档案、攻击阶段、投射物所有权、
命中顺序、射线/寻路预算、死亡清理、保存排除和容量策略。若敌人资源 schema 变化，必须在
合同中声明版本和非法字段降级，不得把这些参数散落到专用敌人类。

最低回归：

- 前摇、命中、遮挡、击退、无敌/冷却窗口、死亡和掉落各只结算一次。
- 投射物不能穿过实心方块，不能跨保存恢复残留，离开活动范围或达到寿命后必须回收。
- 多敌人、快速移动、目标消失、暂停、区块卸载和玩家死亡不突破 actor/投射物/事件队列上限，
  也不突破每 tick 射线或寻路预算。
- 运行战斗定向测试、世界冒烟、相关 Q1 内容规模比较和短时 nominal/stress soak。

明确不做：行为树、Lua AI、通用 Boss 框架、可保存投射物层级、完整护甲槽、附魔、复杂连招、
技能树、PvP 或弹道网络同步。

退出条件：近战接近、远程压制和格挡应对具有可观察差异；墙体遮挡和所有容量边界可靠；
保存、死亡和卸载不留下幽灵投射物或重复奖励。

## N9A/N9B：确定性结构、遗迹与生态战利品

玩家问题：现有五类生态和一座路标能引导首次探索，但重复进入世界时缺少更多可辨认地点、
风险和战利品决策。

内部交付顺序：

1. `N9A` 复用现有 `StructureBuilder` 与确定性 cell hash，先固定结构生成阶段、覆盖优先级、
   单元格所有者、footprint、最大尺寸、最小间距和跨区块投影规则。
2. 所有随机只由 world seed、terrain 版本、结构类型和 cell 坐标派生；不使用 `std::rand`，
   不允许结构生成同步加载相邻区块，也不建立通用结构 Manager/Singleton。
3. `N9B` 增加两类有界结构，建议为遗迹和敌人营地；复用现有箱子系统承载 seed 稳定战利品。
4. 初始战利品由稳定结构实例键生成；实例键可由结构类型、cell 坐标和 terrain 版本组成。
   箱子首次创建后以持久库存为准，不因重载、重新投影或加载顺序再次初始化。
5. 为少量生态增加特有资源、结构权重或敌人组合，不扩张成大规模生物群系重做。

批次开始时建立 `exploration-structures-contract-v1.md`。如果新规则改变未生成区块的身份，
预计引入 terrain v3；旧世界必须继续保持 terrain v1/v2，不能静默升级未探索区块。第一轮
不另建独立“结构生成版本”，结构身份跟随现有 terrain 身份；只有未来出现必须独立演进且有
兼容收益的结构规则时才重新评估。

最低回归：

- 相同 seed、版本、结构类型和 cell 坐标在不同加载顺序、线程调度和保存重开后生成同一结构
  与初始战利品；不得出现同步相邻区块加载。
- 已领取箱子、损坏结构和玩家放置方块不会因重载重新生成或被覆盖。
- v1-v8/后续最新保存 fixture 迁移，terrain v1/v2 世界身份保持；新世界只使用合同指定版本。
- 快速流送 Q1、结构规模场景、资源检查和短时/阶段结束 soak 通过。

明确不做：通用结构编辑器、VoxelModel/VOX 导入系统、结构 Manager/Singleton、村庄模拟、
大型程序化地牢、无限地下城、NPC 社会或跨世界副本。

退出条件：两类地点可由正常探索发现并提供不同风险/奖励；同 seed 结果确定；旧世界不漂移；
结构生成、actor 和战利品均满足预算与幂等边界。

## N10：食物、冶炼与资源经济扩展

玩家问题：当前只有一种食物、冶炼和燃料用途，已有系统能工作，但资源之间的选择和循环仍窄。

计划范围：

1. 食物由 1 种扩展到约 4 种，至少在成本、恢复量和冷却上形成可解释差异。
2. 冶炼结果由 1 类扩展到约 3 类，复用现有固定 tick、三槽和负载语义。
3. 配方由 11 个扩展到约 18-22 个，优先复用作物、敌人掉落和生态资源，避免只增加装饰物。
4. 增加可导出的平衡指标：取得成本、制作/冶炼耗时、恢复效率、库存占用和目标所需数量。
5. 第一轮不增加持续掉血的强制饥饿；先通过玩家路径和数据判断资源压力是否真的不足。
6. 增加资源经济校验器：确认每个主线物品从干净世界可达、每种新增资源同时拥有来源和有效
   消耗点、配方图不存在净增益循环或复制路径，并输出库存容量、保存尺寸和保存耗时比较。
7. 第一轮继续使用精确材料配方和现有单输入/单燃料/单输出三槽熔炉。材料组替换、品质、温度、
   多通道或十二槽熔炉只有真实内容重复证明必要时才能另立合同。

批次开始时建立 `resource-economy-contract-v1.md`，固定定义 schema、材料守恒、批量操作、
暂停/卸载、冷却、容量和迁移规则。只有新增持久字段时才升级保存版本。

最低回归：

- 输入、燃料、输出、制作、食用和掉落在成功/失败/满容量/连点/关闭/保存重载时守恒。
- 暂停和卸载不推进冶炼或冷却，也不进行离线追赶。
- 资源定义、配方图和目标需求无死链；经济校验器证明新世界可通过正常循环取得每个主线物品，
  且不存在无成本或净正产出的循环。
- 与 N7-N9 旅程共同运行综合 fixture，并比较库存规模、保存耗时和内容规模预算。

后续饥饿评估门：只有试玩证明“恢复资源没有决策价值”时才另立小合同；默认可关闭、可调且
非致死，不得在本批暗中加入被动伤害压力。

明确不做：材料组模糊替换、多通道熔炉、温度/品质模拟、复杂加工设备树。

退出条件：至少三条资源来源互相进入制作、恢复、冶炼或胜利准备；玩家有选择而非单一最优
答案；可达性、循环检测、守恒、迁移和性能指标全部通过。

## N11A/N11B：难度档案与可选重玩内容

玩家问题：首个胜利闭环完成后，需要在不引入无限任务和在线系统的前提下提供可控挑战与
再次开世界的理由。

内部交付顺序：

1. `N11A` 增加 Casual、Normal、Challenging 三档世界难度，旧世界明确迁移为 Normal。
2. 用一个有版本的参数快照统一控制玩家/敌人伤害、生成压力和掉落权重；禁止把倍率散落到
   各业务系统或 GameMode 分支。
3. 创建世界时可选择难度；创建后可从暂停菜单修改。修改事务式保存，并在下一个固定逻辑 tick
   统一生效，避免同一 tick 内混用两套参数。
4. 难度写入世界 metadata、世界列表、性能场景身份和测试结果，但不改变 terrain seed 或生成
   身份。旧存档、缺失字段和非法值都安全归一为 Normal。
5. `N11B` 增加少量可选目标或路标完成后的有界重复事件，为胜利后游玩提供方向；它是 P2
   伸缩项，不得阻塞已具备明确胜利和继续沙盒能力的 Beta。

批次开始时建立 `difficulty-replay-contract-v1.md`，固定参数、Normal 默认值、暂停菜单修改、
下个固定 tick 生效、世界 metadata、性能/测试身份、奖励幂等和旧世界迁移。若需要新增持久字段，
合同再决定保存版本号，不提前占用编号。

最低回归：

- 相同 seed、生成版本和难度得到确定结果；旧世界迁移到明确默认档位。
- 三档参数都能走通新世界到胜利的核心路径，不产生零伤害死锁、不可达资源或无界 actor。
- 切换规则、事务失败、备份恢复、世界列表显示和重复事件奖励没有复制漏洞；同一固定 tick 不
  混用修改前后的参数。
- 每档执行定向旅程；对生成压力或 actor 规模变化运行相关 Q1 与短时 soak。

明确不做：程序化无限任务、排行榜、赛季、账号成就、云同步或付费难度内容。

退出条件：N11A 的三档具有稳定且可解释的压力差异，难度和世界身份可恢复；若纳入 N11B，
胜利后活动必须有界、可选、不会重复发奖或破坏原主线。N11B 未纳入首个 Beta 时必须明确
标记为后续伸缩项，而不是伪装成已完成。

## N12A/N12B/N12C：本地化、正式音效与低密度音乐

玩家问题：玩法骨架和可靠性已经明显强于产品表现；程序化占位声音、硬编码文本和反馈层级会
限制 Beta 的整体完成感。

内部交付顺序：

1. `N12A` 在 N7A 已建立的语义化文本 key 上完成主菜单、世界列表、HUD、目标、配方、死亡、
   胜利和诊断入口的 `en-US`/`zh-CN` 覆盖，并处理中文字体、fallback、长文本、极端 UI 缩放、
   字幕持续时间和 Credits。N7A 只搭骨架，不能被计作完整本地化。
2. `N12B` 新增采样文件音效定义和后端能力，用许可证清晰、来源与版本可追踪的正式音效替换
   程序化占位提示；明确缓存、并发、缺文件、缺设备、停止和退出语义。
3. `N12C` 最后增加单音乐通道的流式低密度环境音乐，定义播放、暂停、停止、静音、淡入淡出、
   设备失败、资源缺失和后台线程清理。多通道编排不是首轮目标。
4. 统一胜利、死亡、目标完成、拾取和命中的视觉/声音层级，避免同时争夺注意力。

批次开始时建立 `product-presentation-contract-v1.md`，固定资源 key、fallback、语言选择、
字体覆盖、采样音效 schema、音乐控制句柄、音频生命周期和无设备降级。设置格式只有新增语言、
音乐音量等持久选项时才升版；音频定义只有实际改变资源合同才升版，最终编号在合同中确认。

最低回归：

- 两种语言的 key 集合一致；缺 key、非法 UTF-8、缺字体、长文本和极端 UI 缩放有确定降级。
- 音效/音乐资源进入 manifest、资源包和许可证检查；缺设备或缺文件不阻止加载、保存和退出；
  音效并发与缓存有明确上限。
- 暂停、切世界、回主菜单和退出时流式句柄、线程和音量状态全部回收或恢复。
- Debug/Release 隐藏客户端、截图、相关性能场景和 R3 真人可读性/听感记录通过。

明确不做：数字字符串 ID、本地化脚本运行时、全语种翻译、语音配音、动态下载音乐、四通道
音乐编排、实时 DSP、FMOD 重型迁移或在线音频服务。

退出条件：N12A/B 完成后，中英文核心旅程无硬编码缺口，正式音效、字幕和视觉层级协同；
若首个 Beta 纳入 N12C，则音乐的许可、资源、生命周期、性能和人工体验证据也必须全部可回归。

## BETA-RC：集中封板

BETA-RC 不再增加新玩法，只修复 N7-N12 集成后发现的缺陷，并建立新的可重复产品基线。

必须完成：

1. Windows Debug/Release 全量工程生成、0 错误重建、十三个及后续新增测试目标、资源包、
   隐藏客户端和启动负例全部通过；适用的 macOS 工程、双配置与原生门禁同时通过。
2. 从 v1 到当前保存版本的全部迁移 fixture、所有 terrain 身份和设置版本均有正反例。
3. 只有场景身份确实变化时才重批 Q1 基线；绝不通过放宽阈值掩盖回归。
4. 改过区块、actor、投射物、保存或后台生命周期的批次先执行 60-120 秒 nominal/stress；
   最终再执行 nominal/stress 各 1800 秒正式 Q3。
5. 重跑受控 dump、sidecar、混合栈符号、符号归档、崩溃提示和干净发行包，并记录新哈希。
6. 因 N7/N12 或后续 UI/输入变化重新执行 R3；覆盖创建世界、胜利、容器、制作、熔炉、
   战斗、暂停、焦点、中英文和声音反馈。
7. 重新生成并验证覆盖全部未推送提交的 bundle；创建本地 Beta 标签前确认工作区干净。
8. 执行世界结局迁移、遭遇中恢复和一次性奖励矩阵；证明任何重入点都不能重复完成或发奖。
9. 固化敌人战斗档案、投射物寿命/容量/清理、结构放置/初始战利品快照和资源经济可达性报告。
10. 检查中英文 key 对齐、fallback、字体、资源清单、许可证，以及采样音效/音乐句柄和后台线程
    的完整清理；未纳入首个 Beta 的 P2 伸缩项必须明确标为后续，而不是作为通过项。

退出条件：全部自动和人工门禁通过，迁移/性能/长稳/崩溃/许可证/包身份完整记录；不留未解释
的预算变化、人工跳过项或临时资产。仍不 push，除非用户另行明确要求。

## 明确后置范围

管线已经成为主要阻塞，才单独评估动态 ID 或 mod 平台，不能以“未来也许需要”为理由提前
改写当前可靠的存档和资源身份。
